## Frontend Config ↔ DB Schema Integration Plan

This plan proposes a migration-adjacent workflow that keeps **frontend UI config EDNs** structurally valid and semantically aligned with the **consolidated DB schema**.

It is intentionally **safe by default**:

- **Default mode**: **dry-run + fail-on-mismatch** (no files are rewritten).
- **Explicit enablement** is required to apply changes to config files.

The plan is also **domain-generalized**: it discovers and validates/syncs config for **all domains** under `src/app/domain/frontend/*/config/`.

---

## Context (current state)

### Source of truth: DB schema

- `resources/db/models.edn` is the consolidated schema produced by the migrations system.
- It is generated by `app.template.backend.migrations.simple-repl/merge-hierarchical-models!`.
- It intentionally strips UI/config keys (see `strip-all-admin-config`), so **UI-related metadata must not be stored in** `models.edn`.

### Frontend config files (runtime-editable)

Admin config (template/admin core):

- `src/app/admin/frontend/config/entities.edn`
- `src/app/admin/frontend/config/view-options.edn`
- `src/app/admin/frontend/config/form-fields.edn`
- `src/app/admin/frontend/config/table-columns.edn`

Domain config (example: expenses):

- `src/app/domain/frontend/expenses/config/entities.edn`
- `src/app/domain/frontend/expenses/config/view-options.edn`
- `src/app/domain/frontend/expenses/config/form-fields.edn`
- `src/app/domain/frontend/expenses/config/table-columns.edn`

### Current validator

- `scripts/bb/validate_frontend_config.clj` validates the **shape** of those EDNs using Malli specs in `src/app/shared/specs/*`.
- It does **not** (yet) validate that referenced entities/fields exist in `resources/db/models.edn`.

---

## Goals

1. **Catch mismatches early**: if UI config references an entity/field that no longer exists in the DB schema (or uses inconsistent naming), fail fast with a clear report.
2. **Keep safe defaults**: validation is always safe; synchronization (rewriting config files) is opt-in.
3. **Support many domains**: adding a new domain folder with the standard config EDNs should “just work” without hardcoding paths.
4. **Respect separation of concerns**:
   - DB schema stays DB-focused (`models.edn`).
   - UI-only constructs (computed fields, joins, presentation details) live in UI config files.

---

## Non-goals

- This plan does **not** change the database migration system itself (automigrate) beyond optionally adding an explicit, opt-in post-migrate step.
- This plan does **not** attempt to infer business semantics (labels, formatting, ordering). Syncing is conservative.

---

## Key decisions

### 1) Default is “dry-run + fail-on-mismatch”

- Validation runs will produce actionable mismatch reports and exit non-zero when mismatches exist.
- Sync runs will, by default:
  - compute a proposed patch (additions/removals/quarantine),
  - print a human-readable summary,
  - **not write any files**,
  - exit non-zero if the patch is non-empty (so CI can enforce alignment).
- To write files, the developer must explicitly pass `--apply`.

### 2) Generalized for multiple domains

Domain discovery rule:

- For each directory under `src/app/domain/frontend/*/`, if it contains `config/`, treat it as a domain.
- For each domain, validate/sync these files if present:
  - `entities.edn`
  - `view-options.edn`
  - `form-fields.edn`
  - `table-columns.edn`

Optional behavior:

- Provide allowlist/denylist flags (e.g. `--only expenses`, `--skip expenses`).

### 3) Where computed/virtual fields should be declared

**Computed/virtual fields should be declared in UI config only**, never in `models.edn`.

Rationale:

- `models.edn` is auto-generated and stripped of UI-related keys.
- Computed fields are a UI concern (presentation + computed semantics), not a physical DB column.

Where to declare them today (existing pattern):

- `table-columns.edn` already supports per-entity `:computed-fields`.
  - Example: admin `:audit-logs` defines `:computed-fields` like `:entity-name`, `:admin-email`, etc.

Recommended rule set:

- A computed field may appear in `:available-columns` / `:default-visible-columns` even if it is not in the DB fields.
- A computed field is considered valid **only if**:
  - it appears in the entity’s `:computed-fields` map, OR
  - it is explicitly allowlisted as a UI-only field for that entity.

Form usage:

- If a computed/virtual field is intended to be displayed in forms, it should be declared in `form-fields.edn` and its UI behavior (read-only, display-only) must be encoded in config (future: a formal `:computed?` / `:read-only?` convention).
- As a safe default, the validator can treat form-fields as “DB-backed fields only” unless explicitly marked as computed.

## Definitions and normalization rules

Because the codebase mixes identifier styles (DB snake_case vs UI kebab-case and strings vs keywords), the validator/sync tool should work on a normalized internal representation.

### Entity key

- DB entity keys in `models.edn` are snake_case keywords like `:expenses`, `:email_verification_tokens`.
- UI config entity keys are typically keywords like `:users`, `:expenses`.

Normalization for matching:

- Compare entity keys by `name` (string) exactly (no hyphen/underscore conversion for entities unless the codebase adopts a rule later).

### Field id

Observed in UI config:

- Domain config uses strings like `"purchased_at"`.
- Admin config uses strings like `"full-name"` even when DB field is `:full_name`.

Normalization for matching fields:

- Convert to a normalized string key:
  - if keyword → `(name k)`
  - if string → itself
  - then normalize separators:
    - treat `_` and `-` as equivalent for matching
    - example: `full_name` ↔ `full-name`

Important: the sync tool should **preserve original style** when writing (if/when `--apply` is used), but matching should be tolerant.

## Proposed architecture

### A) Schema index from `resources/db/models.edn`

Create a small library that loads `resources/db/models.edn` and produces:

- `entities`: set of entity keys
- `fields-by-entity`: map of entity → set of DB field names (string normalized)
- `foreign-keys-by-entity` (optional): map of entity → relationships (useful for hints)

This index is the basis for semantic validation and syncing.

### B) Semantic validator (shape + schema alignment)

Extend the existing config validator to include checks like:

- For each entity appearing in any config file: entity exists in `models.edn`.
- For each referenced field in:
  - `form-fields.edn` (`:create-fields`, `:edit-fields`, `:required-fields`, `:field-config`)
  - `table-columns.edn` (`:available-columns`, `:default-visible-columns`, `:filterable-columns`, `:sortable-columns`, `:always-visible`, `:column-config`)
  - `view-options.edn` (`:column-defaults`, `:column-locks` keys)

Validate that field exists in DB *or* is an allowed computed/virtual field.

Output requirements:

- Print a compact summary per file.
- On mismatch, print a structured report:
  - unknown entities
  - unknown fields per entity
  - fields present in DB but missing from configs (informational unless sync is enabled)

### C) Sync engine (opt-in rewriting)

The sync engine produces a patch plan per config file:

- Add missing DB fields into `:available-columns` (conservative append).
- Optionally add missing DB fields into `:create-fields`/`:edit-fields` only if there is a strong heuristic (default: do not).
- If config references removed DB fields:
  - default behavior: quarantine them (e.g., move to a `:removed-fields` bucket) and mark as invalid until applied.

Formatting and comment preservation:

- Many config files include comments and hand-formatting.
- If we support `--apply`, prefer a rewrite that preserves comments/formatting.
  - Recommend using `rewrite-clj` (or equivalent) for EDN AST transforms.
  - If initial implementation uses `pprint`, it should be clearly documented that comments will be lost.

### D) Entry points (bb tasks / REPL integration)

Suggested entry points:

- `bb validate-frontend-config` (existing) → extended to include schema alignment.
- New: `bb sync-frontend-config`:
  - default: `--dry-run` (implicit) + fail-on-mismatch
  - optional: `--apply`
  - optional: `--only <domain>` / `--skip <domain>`

Integration into migration flow:

- Do **not** change `mig/migrate!` to mutate files.
- Add an explicit “post-migrate validation/sync” step:
  - e.g. a new REPL helper: `mig/migrate-and-check-frontend-config!`
  - or a recommended shell sequence in docs.

## Phased implementation plan

### Phase 0 — Documentation and invariants

Deliverables:

- Document normalization rules (entity/field), computed fields rules, and domain discovery.

Acceptance criteria:

- Developers understand where to add domain configs and how the validator interprets them.

### Phase 1 — Semantic validation (no rewriting)

Deliverables:

- Load `resources/db/models.edn` and cross-check config references.
- Add mismatch reporting.

Acceptance criteria:

- `bb validate-frontend-config` fails when a config references missing entities/fields.
- Output clearly indicates what is wrong and where.

### Phase 2 — Sync engine in dry-run mode

Deliverables:

- Patch computation for each config file type.
- Default behavior: print patch summary and exit non-zero if patch not empty.

Acceptance criteria:

- Running sync produces a deterministic, readable patch summary without modifying files.

### Phase 3 — Apply mode with safe editing

Deliverables:

- `--apply` flag that writes changes.
- Prefer comment/format preserving edits.

Acceptance criteria:

- Config files can be updated automatically without losing important comments/structure.

### Phase 4 — Multi-domain hardening

Deliverables:

- Robust domain discovery.
- Allowlist/denylist.
- Add at least one additional test domain fixture in `test/` to ensure discovery works.

Acceptance criteria:

- Adding `src/app/domain/frontend/<new-domain>/config/*.edn` is automatically picked up.

## Migrations workflow (schema changes)

This plan doesn’t change the migration system itself. When you need DB schema changes, follow the repo’s standard migration workflow:

1. **Edit canonical EDN only** (never generated files):
   - `resources/db/template/models.edn`
   - `resources/db/shared/models.edn`
   - `resources/db/domain/models.edn`
   - plus `functions.edn` / `triggers.edn` / `views.edn` / `policies.edn` as needed.
2. **Generate migrations from a REPL**:
   ```clojure
   (require '[app.template.backend.migrations.simple-repl :as mig])
   (mig/make-all-migrations!)
   ```
3. **Apply migrations + verify alignment**:
   ```clojure
   (mig/migrate!)
   (mig/status)
   (mig/check-migrations-alignment! :dev)  ;; optional but recommended
   ```
4. **Do not edit** `resources/db/models.edn` or `resources/db/migrations/*` by hand.

Note: the frontend-config alignment work in this plan is **migration-adjacent** only; the changes applied in this session did **not** require DB migrations.

## Current frontend-config command sequence

Use this after schema changes or UI config edits:

```bash
# 1) Validate config shape + schema alignment
bb validate-frontend-config

# 2) Preview sync changes (dry-run)
bb sync-frontend-config

# 3) Apply sync changes (explicit)
bb sync-frontend-config --apply
```

## Notes: computed/virtual fields (detailed guidance)

### When to use computed fields

Use computed fields when:

- the value is derived (e.g., join display name),
- it is not stored as a column,
- it should be shown in list views.

### Where to define them

- Define computed fields in `table-columns.edn` under `:computed-fields`.
- Keep their dependencies explicit (which DB fields are required to compute it).

### Who computes them

This plan does not mandate where computation occurs, but it must be consistent:

- Backend-computed: via views/joins in the API response.
- Frontend-computed: derived from already-fetched entity data.

The validator/sync tool only ensures the **configuration references are consistent** and that a computed field is declared where it’s used.
